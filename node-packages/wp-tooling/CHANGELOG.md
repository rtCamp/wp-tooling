# Changelog

All notable changes to `@rtcamp/wp-tooling` are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## Unreleased

### Added

- `lens` manifest key — an array of the lens skills that should check a scaffold's output once its tests are green, most relevant first, from a closed list (`accessibility`, `i18n`, `performance`, `security`, `seo`, `vip-readiness`). `validate` rejects a bare string, an empty array, duplicates, and an MCP ability name such as `runtime-health`, which is something a lens reads rather than a lens. `execute()` reports it as `scaffold.lens` and `list --json` as `lens`, both `null` when undeclared, and `null` in `list` for remote scaffolds whose manifests are not fetched. Additive: `result.scaffold` gains one field.
- New `integration` category for opinionated platform integrations, and the first scaffolds to use the reserved `"wizard_step": "integrations"`. Each builds on a `wp` kind, reuses its wiring anchor, and degrades to standard behaviour off the platform.
- `integration/vip-search` scaffold — a `Registrable` that sends heavy meta and taxonomy main queries on one post type to VIP Search through `ep_integrate`, which works on any ElasticPress backend too. Adds `META_KEYS` to VIP Search's post meta allow list (it indexes none by default), preserving whichever list or map format the allow list arrived in, since VIP discards entries that do not match it. Fires a prefixed action whenever a query that asked for the index falls back to MySQL — the silent outcome when query integration is not enabled for the environment, under VIP search rate limiting, or on an index error. Changes only the main query from `pre_get_posts`; secondary queries opt in where they are built. No-ops without `EP_VERSION`.
- `integration/vip-remote-request` scaffold — a service that fetches remote data over GET without an uncached request on the page path. On VIP it delegates to `wpcom_vip_file_get_contents()` (cached, stale-on-failure, backs off a failing host); `vip_safe_wp_remote_get()` is deliberately not used because it caches nothing. Elsewhere it caches successful responses only in the object cache via `rtCamp\WPFramework\Utils\Cache` and fetches with `wp_safe_remote_get()`. Internal hosts are refused on both paths, and only when a request is actually sent, so a cached or stale copy never waits on a DNS lookup. `timeout` and `cache_ttl` are `enum`-constrained to what `RemoteRequestTimeout` (at most 3s) and `LowExpiryCacheTime` (at least 300s) accept.
- `integration/vip-cron` scaffold — a recurring job on wp-framework's `AbstractJob` that runs on exactly one runner. `AbstractJob`'s `schedule_*()` methods do nothing without Action Scheduler, so the job falls back to a WP-Cron event, which Cron Control runs on VIP, and clears that event for a single Action Scheduler action once the library loads. Checks its schedule on `admin_init` only, declares its Cron Control concurrency, and constrains `schedule` to the four WP-Cron schedules core registers. Distinct from `wp/cron`.
- `integration/vip-webhook` scaffold — a REST controller that verifies an HMAC-SHA256 signature over the raw body in constant time, refuses every delivery until a shared secret is set (a VIP environment variable, or a constant of the same prefixed name elsewhere — never written by the scaffold), caps the body at 64 KB, accepts a JSON object or an array (as batch senders post), acknowledges a repeated delivery to the same webhook with 200 without queueing it twice, and queues the payload on Action Scheduler or WP-Cron before answering 202 instead of doing the work in the request. The REST module it wires into is the `module_path` input, so a project whose module is `REST.php` is not sent to a `Rest.php` that does not exist.
- `lint/phpcs/full` on `rtCampWP` and `lint/phpcs/core` on `rtCampWP-Basic`, both from `rtcamp/wp-phpcs`, the standards the v2 plugin and theme skeletons use. Both variants:
  - fill `testVersion` from the `Requires PHP` header (PHPCompatibility aborts on the first line of every file without it), `minimum_wp_version` from `Requires at least`, the text domain from `Text Domain`, and the prefixes from the text domain and the PSR-4 namespace;
  - accept PSR-4 class file names, and exempt block `render.php` files from the global-variable prefix and text-domain-mismatch checks, since core includes them inside a function and they translate with `block.json`'s text domain;
  - lint `tests/`, exempting it from the prefix, VIP file-operation and remote-data, `ini_set` and global-override rules by sniff name. An exclude-pattern on a re-referenced standard such as `WordPress-Docs` has no effect, because its sniffs are already loaded;
  - declare `rtcamp/wp-phpcs` as the only dev dependency, with two `composer.json` wiring entries without which `composer require` fails: the `rtCamp/wp-phpcs` VCS repository, since the package is not on Packagist, and `allow-plugins` for the Composer installer that registers the standards.

  Every PHP file the bundled scaffolds render (42 files from 21 scaffolds, half of them tests) passes both.
- `automattic/vipwpcs` as `lint/phpcs/vip`'s dev dependency, with `allow-plugins` wiring for `dealerdirect/phpcodesniffer-composer-installer`, which WPCS and VIPCS depend on: without it a non-interactive `composer require` exits 1 and no standard is registered. The `setup` skill's install command and `docs/examples.md` use the same package.
- VIP project detection in the `setup` skill, matching `WordPressVIPMinimum`, `WordPress-VIP-Go`, `automattic/vipwpcs`, `VIP_GO_APP_ENVIRONMENT` or `VIP_GO_ENV` across `*.php`, `*.xml`, `*.dist` (including `phpcs.xml.dist`), `*.json` and `*.yml`.
- `tests_namespace` input for `setup/phpunit`, which names `tests/bootstrap.php`'s `@package` after the project's PSR-4 test namespace so the bootstrap passes `WordPress-Docs`.
- `wp-api/speculation` scaffold — generates a `Registrable` that customises WordPress core's Speculation Rules API (core since WP 6.8). Pins the prefetch/prerender `MODE` and `EAGERNESS` through the `wp_speculation_rules_configuration` filter (passing a `null` config straight through, so speculative loading that another filter disabled is never revived) and merges an `EXCLUDE_PATHS` constant into `wp_speculation_rules_href_exclude_paths`. `register_hooks()` no-ops when the API is absent, so the class is safe on WP < 6.8. Wires into the same module and anchor as `wp/registrable`.
- New `wp-api` category for scaffolds that customise a modern WordPress core API, and the first scaffold to use the reserved `"wizard_step": "wp-apis"`.
- Constrained inputs — an input declaration may carry an `enum` of allowed values. `validate` rejects a malformed enum (empty, non-string members, duplicates) and a `default` that is not one of its own members, so an unusable manifest fails at authoring time. At run time the engine checks the **resolved** value (after any `transform`, i.e. what reaches the templates) and throws the new `EINVALIDINPUT` — carrying `invalid[] = { key, value, allowed }` in the `--json` payload — instead of rendering code from a value the target API will silently ignore. Additive: an input without `enum` behaves exactly as before. `wp-api/speculation` constrains `mode` and `eagerness` with it.
- `wp/block-interactive` scaffold — generates a block driven by core's Interactivity API (core since WP 6.5): a `block.json` declaring `supports.interactivity` plus `viewScriptModule`, a `render.php` emitting the `data-wp-*` directives, a `view.js` store, the editor entry points, and a `Registrable` that registers the block from its build output. Deliberately not an `AbstractBlock` subclass — that abstract forces a `render_callback`, which would override `block.json`'s `render`. Registration no-ops before WP 6.5 and before a build has run. Shares the Blocks module and the `// scaffold:wp/block-dynamic:classes` anchor with `wp/block-dynamic`.
- `wp-api/block-bindings` scaffold — generates a `Registrable` that registers a Block Bindings source (core since WP 6.5) through `register_block_bindings_source()` on `init`, with core's exact `get_value_callback` signature, a `USES_CONTEXT` declaration so the callback can read the bound block's context, and a `function_exists()` guard for WP < 6.5.
- `wp-api/script-module` scaffold — generates a Script Module (core since WP 6.5): an ES module plus a `Registrable` that registers it under an `@vendor/name` id, reads dependencies and a cache-busting version from the build's generated `.asset.php`, normalises string dependencies to core's `[ 'id' => ... ]` form, and enqueues it on a hook constrained by `enum`. Stays on the WP 6.5 signature — `wp_register_script_module()`'s `$args` parameter arrived in 6.9.

### Fixed

- `discover_from: composer.json:autoload.psr-4` now resolves **path** inputs (`base_path`, `*_path`, `*_dir`) from the map entry's directory instead of skipping them, grafted the same way namespaces already were — with a root of `Acme\Blog\` → `inc/`, a `base_path` default of `includes/Services` resolves to `inc/Services`. Previously the namespace was grafted but the directory kept the manifest default, so any project not laid out under `includes/` got a correctly-namespaced class written outside its autoload root, where it never loaded. Affects the 12 bundled scaffolds that declare PSR-4 discovery on `base_path`. Projects already using `includes/`, projects without a `composer.json`, and callers that pass `--base_path` explicitly are unaffected.
- Scaffolded PHP now passes `rtCampWP` clean. Rendering all 12 `wp/*` scaffolds into a skeleton consumer produced **105 PHPCS errors** before this release and none after (`use`-ordering, the one thing no template can settle, is now sorted by the engine after rendering — see the entry below). The causes:
  - 24 templates emitted `declare(strict_types=1);`, whose spacing `SlevomatCodingStandard.TypeHints.DeclareStrictTypes` rejects — one error in every file the older scaffolds wrote. `setup/phpunit`'s `tests/bootstrap.php` had no `declare` line at all.
  - 35 bare `@return` annotations restated a native return type without adding a description or a generic shape, which `ReturnTypeHint.UselessAnnotation` rejects. Removed, matching how the hand-written skeleton classes document typed methods.
  - 41 missing docblocks in the older test stubs: no `@package` in the file comment (12) and no doc comment on a test method (29).
  - 5 `use` blocks ordered so `AlphabeticallySortedUses` rejected them under its case-sensitive setting, in the `wp/block-dynamic`, `wp/cli` and `wp/rest` classes and the `wp/cli` and `wp/registrable` test stubs.
- Rendered PHP has its `use` block sorted by the engine, so generated code satisfies `AlphabeticallySortedUses` whatever the consuming project is called. The correct order depends on where the project's own namespace sorts against `PHPUnit\` and `WP_*`, which a Mustache template cannot know: the same test stub needs one order under `Inc\…` and the opposite under `rtCamp\…`. Rendering into a theme namespaced `rtCamp\Theme\Elementary` used to leave an error in **every** generated test file. The sort reproduces the sniff exactly — segment by segment, byte-wise, case sensitive — and is deliberately narrow: a group import, an alias, a `use function`/`use const`, a multi-line statement or a comment inside the block all leave the file untouched rather than risk a bad edit, and indented trait imports are never touched.
- `discover_from: plugin-header:<header-name>` is implemented. Seven `wp/*` scaffolds have always declared `plugin-header:text-domain`, but nothing resolved it — the prefix fell through to `undefined` and every scaffold silently emitted the manifest default `my-plugin`, which is a PHPCS `Mismatched text domain` error in any project not actually called that (twelve of them in a single skeleton run). The engine now reads the entry header, preferring a root `*.php` with `Plugin Name:` and falling back to a theme's `style.css` with `Theme Name:`, scanning only the header comment.
- `discover_from: composer.json:autoload-dev.psr-4` is supported, and every scaffold that writes a test now uses it for `tests_path`. The selector was previously unrecognised — declaring it was a silent no-op — so test stubs went to the manifest default (`tests/<Kind>`) while both first-party consumers autoload *and* collect tests from `tests/php/`. The generated test was not merely unloadable, it was never collected: PHPUnit's testsuite is a directory glob, so the case silently did not exist.
- `validate` rejects a `discover_from` naming a source the engine cannot resolve, listing the ones it can. This is the guard that would have caught the two entries above at authoring time rather than in generated output.
- `release:bump`, `release:changelog` and `release:zip` work on themes. They resolved the project through a `Plugin Name:` header only, so every one of them failed outright in a theme with *no plugin entry file found*. They now fall back to a `style.css` carrying `Theme Name:`, taking the slug from the directory — which is what WordPress keys a theme on — and `release:bump` rewrites the `Version:` header there.
- `release:zip` warns when the payload is far too large to be a release, attributing the bulk to the top-level directories responsible. Building the skeleton with dev dependencies installed plans a **2.6 GB** archive, because `vendor/` is not in the default ignore list — and it should not be, since a plugin that autoloads its Composer dependencies has to ship it. Dropping it by default would quietly produce a broken plugin, so the size is reported instead, pointing at `composer install --no-dev`.
- `wp/rest` no longer generates a controller that fatals on load. `WP_REST_Controller::get_items()` and `get_items_permissions_check()` declare `$request` untyped, so the generated `WP_REST_Request $request` narrowed an inherited `mixed` — which PHP rejects outright: *"Declaration … must be compatible with …"*, taking down the whole request. Both now take `mixed $request`, which satisfies the parent, the `ParameterTypeHint` sniff and PHPStan's non-ignorable `method.childParameterType` alike; the real type is documented in prose, and `get_items_permissions_check()` carries an explicit `@return bool` because the inherited annotation is `true|WP_Error`.
- Generated tests no longer fire a global action hook to trigger their own registration. `wp/shortcode` called `do_action( 'init' )` and `wp/settings-page` called `do_action( 'admin_init' )`, which re-run every *other* listener on those hooks — in a real project that means duplicate block registrations and headers sent after the harness flushed them, both of which `WP_UnitTestCase` fails on. They now call `register_shortcode()` and `register_settings()` directly. `wp/rest` had the mirror-image bug — it called `register_routes()` outside `rest_api_init`, the only context where `register_rest_route()` is legal — and now goes through the hook.
- `wp/admin-page` no longer emits a comparison that is always true. The template rendered `$parent = '{{parent_slug}}'; return '' === $parent ? null : $parent;`, so leaving `parent_slug` at its default — every top-level page — produced `'' === ''` and a PHPStan `identical.alwaysTrue`. The template now selects the branch at render time and emits either the literal or a plain `return null;`.
- `wp/block-dynamic` emits `protected function get_block_dir(): string`. It was `public ... : ?string`, widening the visibility `AbstractBlock` declares (the same divergence fixed above for `get_classes()`) and keeping a nullable half the body never returns.
- `wp/cpt`, `wp/taxonomy` and `wp/user-role` label accessors satisfy the framework's `@return non-empty-string`. `__()` is typed `string`, so at PHPStan level 8 — which `theme-elementary` runs — five accessors failed the inherited contract; they now fall back to the untranslated literal.
- `wp-api/script-module` builds its dependency entries key by key instead of passing the caller's array through, so the result is exactly the `array{id: string, import?: string}` shape `wp_register_script_module()` documents rather than whatever else the array carried.
- `wp/block-interactive`'s test docblock starts with a capital, which `Generic.Commenting.DocComment.ShortNotCapital` requires and consumers that lint `tests/` enforce.
- `wp/module` now emits `protected function get_classes()`, matching the `abstract protected` the framework's `AbstractModule` declares and the visibility every hand-written module uses; scaffolded modules were the only ones widening it to `public`. Its generated test reaches the method through reflection, since the module is `final`.
- `wp/module`'s generated test no longer fails a consumer suite on the run that creates the module. `test_each_listed_class_is_loadable` asserted only inside a `foreach` over the class list, which is empty in a freshly scaffolded module — no assertion recorded, so PHPUnit marked the case risky and consumers run with `failOnRisky`. It now compares the whole list against the loadable subset.
- The scaffold skill now states outright that it must not wire a class into a spot a later `wp-tooling init` deletes. rtCamp skeletons wrap optional capabilities in `// wp:example:<key>` … `:end` regions and `init` removes a dropped region body and all, but the insertion rule was "after the last sampled occurrence" — which in `Main::CLASSES` is the last line *inside* such a region. `SKILL.md` and `docs/ai-orchestration.md` now refuse that placement at every fall-through level, anchors included. Hardening rather than a repair: on the eval fixtures the previous wording already landed the snippet outside the region, so this makes a safe behaviour a stated rule instead of an inference.
- `validate.js` derives its manifest key allow-lists from `schema.js` instead of restating them. The two carried independent copies of the same seven lists, so a key could be accepted by the schema and rejected by the validator that actually runs; adding `enum` needed both edits and nothing would have caught doing only one.
- A `wiring` entry whose `target_file` still resolves outside the project after normalisation is dropped with a warning rather than handed to the AI to edit. `path.posix.normalize` collapses interior `..` but keeps a leading one, so a single-segment path input reached above the project root.
- `docs/wp-framework-contract.md` documented `get_classes()` as `public` and described the wiring snippet as going *above* the module's marker comment, contradicting both the skill and `docs/ai-orchestration.md`.

## [1.0.0] - 2026-07-30

### Added

- Remote scaffolds — a scaffold's `scaffold.json` + templates can live in another repo. `scaffolds/sources.json` lists the source repos (pinned `{ repository, ref, path }`); each repo publishes a `scaffolds/index.json` enumerating the scaffolds it offers, which the registry fetches to discover them (one PR in the owning repo adds/changes a scaffold; wp-tooling only changes to onboard a new repo). Manifests + templates are fetched on `add`, cached under `${XDG_CACHE_HOME:-$HOME/.cache}/wp-tooling/remote/` and validated with ETag conditional requests (`304 Not Modified` serves the cache; movable tags refresh when they move). New error code `EFETCHFAIL` (network/HTTP) distinct from `EBADSCAFFOLD` (bad index/manifest). `list` is online-preferred with a cache fallback and reports unreachable sources as warnings; `validate --remote` fetches + schema-validates each index + manifest; `wp-tooling cache clear` empties the cache. Dormant by default — no `sources.json` ships.
- Engine-side input discovery (`discover_from`) — an input declaration can say where to source its value from the project, so the engine fills it instead of the caller guessing. Resolves from `composer.json` / `package.json` (dotted paths; `autoload.psr-4` yields the root namespace) and `.wp-tooling.json`, with precedence `supplied → discovered → default`. Fail-safe: a missing or malformed project file falls through to the input's `default`, so a project without those files behaves exactly as before the resolver existed. Adds an optional `transform` step for derived inputs (`json-escape` doubles backslashes for the PSR-4 composer key). The inputs the engine actually rendered with are surfaced on `execute()` as `engine.inputs`. Bundled `setup/psr4` + `wp/*` scaffolds annotated with `discover_from`.
- Feature toggle layer — a scaffold may declare an optional `feature` block (`config_key`, `owned_files`, `confirm_remove`, `gitignore`) marking it as a toggleable project feature. New TTY-free `enable` / `disable` / `status` verbs create or remove the owned files idempotently, manage `.gitignore` lines (Mustache-rendered against resolved inputs), prompt before deleting consumer-editable files (`confirm_remove`, overridable with `--force`), and persist on/off state in `.wp-tooling.json`. New `wp-tooling features` command — lists feature status by default, with `--enable` / `--disable` to toggle (plus `--json`, `--force`, `--no-install`, `--dry-run`); `setup/tailwind` ships as the first such feature. Additive — the `feature` block never affects the `add` / `execute` path.
- TTY UI kit (`src/ui/`) with nine public exports: `Wizard`, `text`, `confirm`, `password`, `checkbox`, `radio`, `checkboxTree`, `spinner`, and `CancelledError`.
- `Wizard` class -- runs steps in order, sharing a mutable context object; supports `skip(ctx)` predicate. Validates that `steps` is an array. Omits ANSI formatting in non-TTY mode.
- `spinner` -- async progress feedback with ASCII animation in TTY and plain text fallback. Guards against multiple intervals when `start()` called twice.
- `text`, `confirm`, `password` prompts with validation support and non-TTY fallback. Each accepts either a string message shortcut (`text('Name?')`) or a full options object.
- `checkbox` (multi-select) and `radio` (single-select) flat list selects with input validation (`TypeError` on missing or invalid `choices`).
- `checkboxTree` -- grouped tree multi-select with group-level toggling. Returns selections in display order. Input validation for `groups`. Returns empty array for empty groups without prompting.
- `CancelledError` -- thrown on Ctrl+C in any TTY-interactive prompt or select (including `text` and `confirm`, which surface cancellation through the underlying `readLine` SIGINT handler). Callers decide exit behaviour.
- Low-level terminal helpers (`src/ui/core/terminal.js`) -- ANSI codes, cursor control, keypress events.
- Jest test suite for all UI primitives (75 tests, including dedicated coverage for `src/ui/core/terminal.js`).
- `@rtcamp/wp-tooling/ci` — `detectChanges` library function. Buckets changed files into css / js / php / gha counts against the diff base (auto-detected from `GITHUB_BASE_REF` for PRs, push event `before` SHA from `$GITHUB_EVENT_PATH` for pushes, `HEAD~1` as a last resort). Opt into per-bucket file lists with `{ includeFiles: true }`. Zero runtime dependencies.
- `wp-tooling` CLI (`bin/wp-tooling.js`) — top-level dispatcher with subcommand registry, `--help`, and `--version`. `main()` always returns `Promise<number>`; a `CancelledError` thrown from any TTY UI primitive is caught centrally and mapped to exit code 130 so individual subcommands need no Ctrl+C handler. Unhandled rejections render as a one-line `wp-tooling: unexpected failure (...)` instead of a Node stack trace.
- `wp-tooling detect-changes` subcommand. Supports `--output text|json|github`, `--ignore <regex>`, `--base <ref>`, `--files <path|->`, `--include-files`, and `--dry-run`. `--include-files` adds `<bucket>-files` arrays alongside counts (newline heredoc under `--output github`, space-joined under `--output text`, native arrays under `--output json`) so workflows can lint or test only the changed paths. With `--dry-run` and `--output github`, the would-be `$GITHUB_OUTPUT` lines are printed to stdout (prefixed with `[dry-run]`) instead of being appended to the file.
- `@rtcamp/wp-tooling/release`: three release-flow libraries plus matching `wp-tooling` subcommands. Shared `loadContext()` reads `package.json`, optional `composer.json`, and locates the WordPress plugin entry file at the package root.
- `wp-tooling release:bump` subcommand. Accepts `--type patch|minor|major` (default `patch`) or an explicit `--to X.Y.Z`. Rewrites `package.json`, `composer.json` (if present), the plugin header `Version:` line and the matching `*_VERSION` constant. Writes are atomic per file. Supports `--dry-run`. Exits 1 when the plugin entry file or its `Version:` header is missing.
- `wp-tooling release:changelog` subcommand. Renames `## Unreleased` to `## <version> - <YYYY-MM-DD>` (UTC) and prepends a fresh `## Unreleased`. Reads the version from `package.json` by default; `--to X.Y.Z` overrides. Refuses to run when `## Unreleased` has no notes. Supports `--dry-run`.
- `wp-tooling release:zip` subcommand. Builds a deterministic `dist/<slug>-<version>.zip` containing the slug-named top-level directory. Reads `.distignore` when present; falls back to a default exclude list (`tests/`, `node_modules/`, `bin/`, `.github/`, `*.config.js`, `package-lock.json`). Entry mtimes pin to `SOURCE_DATE_EPOCH` / `git log -1 --format=%ct` / `2010-01-01` (in that precedence order); entries are sorted lexicographically; two consecutive runs against the same tree produce a byte-identical archive. Supports `--dry-run` and `--force`.
- Hand-rolled zip writer (`src/release/zip.js`) on top of `zlib.deflateRawSync`. Implements the standard ZIP local file header, central directory, and end-of-central-directory record. Roughly 100 lines, keeping the zero-runtime-dep guarantee.
- `@rtcamp/wp-tooling/hooks` — `installHooks` library function. Copies the bundled POSIX `commit-msg` (Conventional Commits validator) and `pre-commit` (`npm run lint:staged` runner) templates into the active git hooks directory. Resolves submodule and linked-worktree layouts via `git rev-parse --git-common-dir`. Zero runtime dependencies.
- `wp-tooling install-hooks` subcommand. Supports `--force` (overwrite existing hooks, including Husky-managed ones) and `--dry-run` (print planned actions without writing). Existing hooks are detected and the skip hint names Husky explicitly when a Husky signature is present. Each installed hook carries a `# wp-tooling install-hooks v<X.Y.Z>` header so future runs can spot drift.
- `@rtcamp/wp-tooling/version-monitor` — detects dependency updates Dependabot does not cover and applies them. Six detectors (npm packages, GitHub Actions, PHP target, Node LTS, WP-CLI, container base images), a hand-rolled `.github/version-monitor.yml` loader, a per-source updater, and a markdown PR-body reporter. Skips floating pins, pre-releases, and (by default) major bumps; uses `GITHUB_TOKEN` when present. Zero runtime dependencies — Node's `https`/`fs` only.
- `wp-tooling version-monitor` subcommand. `--detect` runs the enabled detectors and prints the updates as JSON; `--apply` reads that JSON from stdin and rewrites the source files (`--allow-major` to include major bumps, `--dry-run` to preview); `--report` reads the JSON and prints a markdown PR body grouped by source. Refuses to run `--detect` with a missing config, naming `.github/version-monitor.yml`.
- **Scaffold engine** (`src/scaffolds/`) with `ScaffoldRegistry`, hand-rolled JSON-schema validator, minimal Mustache-style renderer, and `execute()` programmatic API returning the four-block result shape (`scaffold` / `engine` / `developer` / `ai`). Engine core has zero runtime dependencies and zero TTY UI coupling, so it works from AI orchestrators, CI scripts, and headless harnesses. Implements WTL-02, WTL-06, WTL-07.
- **Manifest extensions** in `scaffold.json` (WTL-07): optional `inputs[]` (project-portable variables with `discover_from` hints and transforms), `wiring[]` (cross-file registration snippets the caller applies with consent), `tests[]` (PHPUnit/Jest/actionlint/yaml-parse stubs), `secrets[]` (declarations only, never values).
- **`bin/wp-tooling` dispatcher** with auto-registration of subcommands from `src/cli/commands/*.js` (5-line thin shims that lazy-require their library's `runCli`). Drop a new command file in; no edit to the dispatcher required.
- **`add` subcommand** (`src/scaffolds/add.js`, shimmed via `src/cli/commands/add.js`) wrapping `registry.execute()` with two modes: interactive (4-step TTY UI `Wizard`: discover, resolveInputs, confirm, execute) and non-interactive (`--non-interactive` / `--json` for AI and CI). Supports `--dry-run`, `--cwd`, and per-input flags. Implements WTL-06.
- **Default scaffold catalogue** under `scaffolds/` bundled with the package (WTL-09): four representative scaffolds covering all three source repos and four scaffold kinds: `wp/cli` (PHP code + PHPUnit test stub), `utility/cache` (`source: package` wrapper around `rtcamp/wp-php-toolkit`), `block/dynamic` (Gutenberg block with edit.js + render.php + block.json + index.js), `ci/cd-wporg` (workflow stub that `uses:` `rtCamp/wp-shared-workflows`, with declared `secrets[]` and `actionlint` validation).
- **Two-directory `ScaffoldRegistry.scan()`** that merges wp-tooling's bundled `scaffolds/` (defaults) with the project's `bin/scaffolds/` (project overrides). Each entry is tagged with `origin: 'default' | 'project'`. Implements WTL-09.
- **AI orchestration contract documentation** at `docs/ai-orchestration.md` (WTL-08). Twelve sections covering engine guarantees, skill responsibilities, error codes, project introspection (PSR-4 + class-suffix + namespace-substructure + block-slug + workflow-filename sampling), adaptive wiring (canonical vs translated snippets, fall-through location resolution, anchor restoration), the wiring permission protocol, the TDD-with-AI loop, and workflow-scaffold orchestration with the secrets checklist.
- **`list` subcommand** (`src/scaffolds/list.js`, shimmed via `src/cli/commands/list.js`): lists every scaffold in the merged catalogue grouped by category, with `--json` for AI consumption, `--category=` and `--origin=default|project` filters, and `--cwd` for project-local scoping. JSON entries carry id / kind / origin / description plus counts (inputs, wiring, tests, secrets) so an AI can pick the right scaffold without reading each manifest.
- **Copy-pasteable AI skill** at `skills/scaffold.md` plus a `skills/README.md` with install instructions. The skill is a single Markdown file with Claude Code front-matter (`name`, `description`) that any project can drop into `.claude/skills/scaffold.md` (or any equivalent path for other AI orchestrators). Built from the `docs/ai-orchestration.md` contract and includes the full discover → introspect → invoke → wire → test → report flow with explicit hard prohibitions on auto-installs, secret-value handling, and admin-surface edits.
